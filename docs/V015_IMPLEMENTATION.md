# EraScript v0.15 — Project-aware module runtime

Status: implementation complete; verification complete

Issue: #12

## Goal

v0.15 removes the module-resolution mismatch caused by the v0.14 temporary generated runtime entry.

EraScript now keeps the original `.era` file URL as the Node module identity while compiling EraScript through a Node ESM customization hook.

## Runtime architecture

```text
project/src/main.era
      |
      +-- import "./helper.era"
      +-- import "./helper.mjs"
      +-- import "viem"
      |
      v
Node original module resolution
      |
      +-- *.era -> EraScript load hook
      |            -> compile
      |            -> composed original-source map
      |            -> inline source map
      |
      +-- *.js/*.mjs/*.cjs -> Node default loader
      +-- npm package      -> Node default resolver
```

No generated entry JavaScript is moved to an OS temporary directory.

## Typecheck architecture

Every loaded EraScript source has a checker-only virtual TypeScript identity:

```text
/project/main.era
  <-> /project/main.era.__erascript__.ts

/project/helper.era
  <-> /project/helper.era.__erascript__.ts
```

The custom CompilerHost:

- resolves explicit relative `.era` specifiers,
- lazily transforms imported EraScript modules,
- delegates ordinary package/JavaScript/TypeScript resolution to TypeScript,
- stores one original-source coordinate map per EraScript module,
- remaps diagnostics back to the correct original module,
- aggregates Web3 diagnostics and unsafe-boundary evidence across the EraScript graph.

The public `typecheck(source, fileName)` API remains compatible.

## Project configuration

`era init` already generated:

```json
{
  "entry": "src/main.era",
  "outDir": "dist"
}
```

v0.15 now consumes the project entry for:

```bash
era run
era check
era check --json
```

when no explicit file is supplied.

An explicit file always wins:

```bash
era run alternate.era
```

Project discovery walks upward from the current directory looking for `era.json`.

Malformed configuration, a non-`.era` entry, or a missing entry file fails explicitly.

## Runtime source maps

The loader uses the existing v0.13 composed Source Map V3 output.

The external map comment generated by TypeScript is replaced by an inline data-URL map so Node can use `--enable-source-maps` while the actual runtime URL remains the original `.era` URL.

No second stack parser or mapping algorithm was added.

## Node compatibility

The runtime loader is registered through `node:module.register()`.

The package engine floor is therefore now:

```json
{
  "node": ">=20.6.0"
}
```

The authoritative v0.15 CI environment remains Node 22.

## Regression coverage

`test/project-runtime.test.ts` verifies:

- imported EraScript type errors map to the imported original file and line,
- `era run` executes `.era -> .era` imports,
- relative JavaScript imports preserve original-project resolution,
- bare `viem` package imports use native npm resolution,
- runtime throws from imported EraScript modules map to the imported original `.era` line,
- `era.json` provides implicit `run`/`check` entry,
- explicit CLI files override project configuration.

Existing v0.14 tests continue to verify:

- argument passthrough after `--`,
- child exit status,
- original-source runtime stack mapping,
- no leaked EraScript runtime temp directories.

## Intentionally deferred

That requires a separate output-layout/import-rewrite contract and should be implemented independently now that runtime/check module semantics are stable.
